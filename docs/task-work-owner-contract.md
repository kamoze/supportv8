# Native Tasks work lifecycle

This source contract is disabled unless `SUPPORT_TASK_WORK_ENABLED=true`. It does not qualify or activate a deployed environment.

An authenticated Runtime Support manager may GET `/api/runtime/tickets/:id/task-work` for the exact current ticket snapshot and digest, then POST an explicit work request to that same route. The request supplies a UUIDv4 idempotency key, expected ticket digest, and the actual Tasks project/work/acceptance inputs. Current Registry membership, the managed installation, native workspace binding and ticket snapshot must agree. The transaction captures the requesting principal, ticket version, complete work request and immutable outbox event. It does not invent a project, owner, investigation, acceptance criterion or production authority.

The attached Temporal worker claims one generation-fenced delivery at a time. It requests the dedicated Identity `servicev8.task-work.v1` profile through `/v1/tokens/task-work`, selecting only the immutable outbox UUID. Identity authenticates a separately registered app workload and reads `/api/v1/internal/task-work/issuance-policy` using its own purpose credential. The policy freshly resolves current manager and installation authority. The issuer owns all account, tenant, source revision and full-event digest claims. The sender publishes the direct CloudEvent to Tasks, accepts only the exact scoped receipt, and stores the returned work link atomically under the lease fence.

`/api/internal/tasksv8/outcomes` receives only that dedicated issuer profile and a direct full CloudEvent. The canonical scope comes from its signed binding. Support accepts a real `tasks-human-verification` receipt with evidence; Dominion health receipts do not substitute for human verification of Support work. Tasks is responsible for the immutable receipt, exact completed execution/specification, current accountable owner and atomic acceptance. Support rechecks its own current source, manager and managed lifecycle, locks the native ticket at commit, and checks credential expiry after lock waits. Replays converge to one immutable receipt. Recording an outcome never closes the ticket.

A changed ticket or revoked manager leaves a stale pending request denied. There is no automatic supersession: an earlier issued token or uncertain delivery cannot safely be canceled locally. Operators must reconcile uncertain deliveries before another source generation can be admitted.

The same manager GET returns `taskWork: null` before a request exists, or the current `requestId`, `sourceRevision`, `workId`, intake state/saved receipt and recorded outcome receipt. This bounded historical read exposes no request body, worker lease, credentials or issuer policy. It repeats current reader and original requester authorization, then rechecks the native ticket/source after those reads. Source drift or revocation denies the read; reading a saved receipt never renews verification or grants publication authority. Query parameters are rejected.

## Activation prerequisites

Apply migration `013_task_work_lifecycle.sql` through the existing reviewed GitOps database process. Do not manually run it on production. The app role must remain restricted; the migration revokes application update/delete/truncate access to immutable lifecycle tables and grants only bounded definer functions.

Provision dedicated Identity caller and policy-reader registrations, their exact audiences/scopes, mounted secret files, issuer/JWKS URLs and the actual Tasks endpoint. Runtime configuration uses `SUPPORT_TASK_WORK_IDENTITY_ISSUER`, `SUPPORT_TASK_WORK_IDENTITY_JWKS_URL`, `SUPPORT_TASK_WORK_TASKS_CLIENT_ID`; `SUPPORT_TASK_WORK_POLICY_WORKLOAD_ISSUER`, `SUPPORT_TASK_WORK_POLICY_WORKLOAD_JWKS_URL`, `SUPPORT_TASK_WORK_POLICY_CLIENT_ID`, `SUPPORT_TASK_WORK_POLICY_SUBJECT`; and the `SUPPORT_TASK_WORK_ISSUER_{URL,CLIENT_ID,SUBJECT,SECRET_FILE,WORKLOAD_ISSUER,WORKLOAD_JWKS_URL}` fields. `SUPPORT_TASK_WORK_TASKS_URL` is the exact HTTPS origin. No shared/default signing secret, identity header or unscoped app credential is a substitute.

The SQL acceptance lane is mandatory in CircleCI and checks real restricted-role capture, rollback, isolation, immutable replay, lease fencing, manager request authorization, concurrent source changes and credential expiry during lock waits. The cross-owner composition is hosted by the pinned Tasks owner lane with actual Support, Identity and Tasks modules. Its Registry and execution observations are isolated fixtures; live Tier2 qualification still requires real qualified instances and the deployed manifest.
