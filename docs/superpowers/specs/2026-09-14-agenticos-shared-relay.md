# AgenticOS adapter in the shared SupportV8 chat relay

Extend the existing SupportV8 relay process, preserving SupportV8's delivery wire format and channels. Runtime PostgreSQL journal PR40 is merged at2b65ee2, but not live. This application change is enabled only through explicit configuration; GitOps credentials, Redis ACLs, network policy, scaling and Runtime SSE/browser recovery are subsequent integration work, not completed by this adapter.

## Contract

- SupportV8 remains enabled as today. AgenticOS is opt-in with `RUNTIME_CHAT_RELAY_ENABLED=true`; require `RUNTIME_CHAT_RELAY_DATABASE_URL` and `RUNTIME_CHAT_REDIS_PUBLISH_URL` when enabled. Disabled mode must not instantiate Runtime clients or require those secrets. Never fall back to Support credentials.
- Runtime database pool max1, connectionTimeoutMillis5000, statement_timeout5000, query_timeout6000, application_name `agenticos-chat-relay`. Production URL comes through shared PgBouncer. No new dependencies.
- Runtime SQL calls only `runtime_chat.claim_delivery($1)`, `complete_delivery($1,$2)`, `fail_delivery($1,$2)`; optional backlog function exists but is consumed by KEDA independently. Claim accepts1..100 and returns `event_id,thread_id,sequence,event_type,scope_hash,lease_id`. Complete/fail return boolean. Lease expiry is30seconds, failure retry5seconds, enforced by PostgreSQL. Never modify any execution or effect state.
- Claim mapping must validate UUIDs, exactly64 lowercase hex scope hash, canonical positive decimal string sequence at most9223372036854775807, and the fixed event union. Preserve sequence as a string; numeric results are rejected, not rounded. Event types: message/turn/recipient/recipient_link `.created|.updated|.deleted`; assistant `.waiting|.updated|.settled`.
- Redis keys `sv8:chat:stream:v1:agenticos:<scopeHash>`, channels `sv8:chat:live:v1:agenticos:<scopeHash>`. Exact JSON notification has only `{eventId,threadId,sequence,eventType}`. Never publish scope hash, lease ID, account/member IDs, transcripts, model output or credentials as fields.
- One Redis MULTI/EXEC contains XADD MAXLEN ~1000 * event <json>, EXPIRE86400, PUBLISH <same json>. Inspect every command result, including XADD ID, expiry1 and publish nonnegative subscriber count. Any error/null/invalid result fails delivery; no DB completion on partial or ambiguous success. PostgreSQL recovery and event-ID deduplication tolerate duplicate notifications. No Lua.
- AgenticOS Redis options: lazyConnect, enableReadyCheck=false, disableClientInfo=true, db0, enableOfflineQueue=false, connectTimeout5000, commandTimeout5000, maxRetriesPerRequest1; finite retry delay. Add a sanitized error handler, never emit raw provider errors or URLs. Dedicated ACL allows only PING/QUIT/XADD/EXPIRE/PUBLISH/MULTI/EXEC and the scoped namespace. Reject nonzero Redis db config. Cleanup must terminate clients even during outages.
- Processing acknowledges only after confirmed Redis success. False complete is stale, not delivered. Failed publications attempt fail(event,lease); false/throwing fail must not prevent other records being attempted. Report only counts and fixed error categories, never raw exceptions. A stuck/failed source cannot prevent the other loop progressing.
- Run Support and Runtime as independent bounded loops in the same existing process. At most one batch in flight per adapter, default batch25 for Runtime (validate1..100), existing Support batch remains bounded. Empty batch delay250ms; failures backoff1000ms. No spin loops on rejected configuration. Runtime queries/commands bounded as above. Support wire format and API behavior remain compatible.
- `/live` reports process alive until stopping; `/ready` and `/health` succeed if at least one configured adapter has a successful attempt within30seconds. A successful attempt means empty successful claim or at least one confirmed delivery. Report per-source readiness with fixed names and counts, no secrets. This lets the healthy source continue during another source outage. Initial readiness awaits a successful attempt. Graceful shutdown stops admission for both loops and closes all clients with a bounded10second drain, then disconnects outstanding transports. Do not restart solely because one dependency fails.

## Verification

Unit tests cover exact reference-only payload, string precision beyond2^53, strict invalid event rejection, atomic Redis results and errors, no ack on failure, false/stale ack, failed fail handling, disabled/misconfigured Runtime, independent loop progress with one stuck/erroring source, readiness transitions and shutdown. Keep existing Support chat tests passing. Add a real isolated Redis integration test (opt-in URL) proving live Pub/Sub, stream replay, TTL, and duplicate publication after a simulated pre-ack crash. Use fresh private namespaces; never production Redis. Local PostgreSQL storage tests already cover role/lease SQL; adapter tests must verify the exact function call interface. No claim of production shared delivery until the subsequent deployment gates pass.
